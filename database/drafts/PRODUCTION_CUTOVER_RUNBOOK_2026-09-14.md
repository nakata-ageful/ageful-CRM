## 1. 適用前に揃えるもの

1. 本番のカタログ全体を読み取り取得する。新しいread-only preflightは列/型/null/default、制約、トリガー、ポリシー、関数定義hash/ACL、テーブル/シーケンスACLを取得する。これはバックアップではない。
2. 復元できるDBバックアップを取得する。アプリJSONだけではDDL/シーケンス/Auth/Storageを復元できない。PostgreSQLバックアップにはスキーマ、データ、シーケンス、所有者/権限の扱いを含める。認証/添付ファイルはサービス仕様に合った別保全も必要。秘密情報をGitに置かない。
3. 独立した検証用Supabaseを用意する。本番の所有者変更/架空請求をテストとして実行しない。個人情報コピー先は明示し、不要なら架空データでAuth/RLS/通常Appを先に検証する。
4. 検証環境へ本番DDLを復元し、追加SQLを適用。JSONから型を推測して作ったPGliteスキーマでの成功を代用しない。
5. 元8表の全値、全新テーブル、シーケンス、FK、監査、未ログイン/別ユーザー拒否を復元先で照合する。

## 2. DB差分の確定

- 現在の本番は新方式未導入のためfresh導入経路が候補。ただしローカルschema.sqlを正本にせず、実カタログとの照合を完了してから適用SQLを固定する。
- 適用順の基準は `tests/billing-runtime-rehearsal.cjs` の明示リスト。ファイル名順やdraft全件一括実行はしない。別実験向けのRPCを混在させない。
- `20260909_billing_runtime.sql` は既存表のRLS/権限も変更する。既存の匿名アクセスアプリを動かしたまま先行適用すると利用不能になるため、切替停止時間内で行う。
- 既存関数、既存トリガー、既存シーケンスの権限も点検。テーブルGRANTだけで新規ID採番の権限が揃うとは限らない。
- 原子的DDL適用の成功と、その後のデータ移行/公開の成功は別。工程ごとの保存点と判定結果を記録する。
- 匿名全面許可へ戻すSQLを安易な復旧策にしない。アクセス保護の解除は別途承認を要する。

## 3. 通常アプリ全体の受入試験

同じビルドを独立Supabaseへ接続し、通常のApp入口から実施する。

1. 未ログインでデータを取得できない。指定ユーザーのログインが成功し、別ユーザーは拒否される。
2. 発電所一覧→詳細→所有者変更。A→B、契約項目保持/変更/クリア、次回A/以降Bと次回Bを確認。
3. 請求書/振替の4通りで、予定→発行/振替結果→入金→訂正まで保存・再取得する。
4. 顧客A/B、請求、ダッシュボード、CSVの請求先/金額/期間/日付が一致する。
5. 個別長期と次期の重複拒否、保守だけ終了/全取引終了/再開を確認する。
6. 保存直後に画面を閉じ、開き直して同一操作の復旧を行い、履歴・金額・回が二重作成されない。
7. 別接続で古い版の更新を拒否し、旧クライアントの保存を拒否する。
8. ブラウザーのCSVダウンロード先ファイルを開き、独立読み取り結果と照合する。

この試験結果と確認用URLをユーザーへ提示し、画面確認を得る。隔離部品画面の確認だけで代替しない。

## 4. 本番切替

1. ユーザーの画面確認・反映GO、検証結果、対象コミット、対象DB、公開先2系統を固定する。
2. 操作停止時間を確保し、古い画面も閉じる。直前バックアップと最新データを取得し、件数だけでなく全値/hashを照合する。
3. 差分があれば移行根拠を再検証。過去の確認ファイルのhashを無条件で更新しない。
4. 確定したDDLと移行を実施。元年次記録の削除/再入力はしない。加古川record51第1回対応＋12月第2回予定165000、天草record61個別期間は最新元データ一致を再検証して実施する。
5. 契約から計算していた将来予定の初期保存と一覧照合を完了する。過去30回の照合成功だけでは将来予定の網羅を証明しない。保守開始日未入力は推定補完しない。
6. `future_schedule_coverage_verified` は照合証跡が揃うまでfalse。利用ユーザー、DBのenabled、アプリflagを整合させる。
7. 承認済みビルドを公開し、実データは読み取り中心に照合。架空の所有者変更/発行/入金は本番に作らない。
8. 一致を確認して運用再開。最新バックアップの所在、復旧担当/手順、対象コミットを記録する。

## 5. 失敗した場合

| 失敗時点 | 対応 |
| --- | --- |
| DDLトランザクション未確定 | ROLLBACKし、元カタログ/行値が一致することを確認。接続切断なら確定状態を調べてから再実行。 |
| DDL確定後・まだ新しい業務入力なし | 操作停止を維持。現在状態も保全し、検証済み復旧先へ復元・照合して切り戻す。旧アプリだけ戻して終わりにしない。 |
| 新方式で業務入力が発生済み | 過去バックアップを本番へ上書きしない。新しい入金/移転/訂正を保全し、別復旧先で差分を照合。原則は修正版による復旧を優先する。 |
| 保存結果不明 | 操作ID/履歴で確定済みか確認。同じ操作IDの再送を使用し、新IDでやり直さない。 |

`enabled=false`やフロントflag OFFだけでは、追加済み権限/トリガー/新方式の実績は元に戻らない。
復旧は「旧ファイルを戻す」ではなく、DB・権限・アプリ・移行後差分を揃えて照合する工程とする。
