# 請求移行の読み取り専用検証

最新：D-025の既存請求先確認を適用する場合は、第3ファイル引数としてRECIPIENT_APPROVAL.jsonを渡す。`datasetHash`（バックアップ全体のcanonical SHA-256）、`mode: "existing_current_customer"`、`basis`を必須とし、対象内容が変われば拒否する。承認なしでは従来どおり請求先を推定しない。承認を適用してもreadyToWrite=false。本番の移行・将来所有者への自動付替えではない。

監査CLIは既存バックアップJSONを読むだけで、環境変数・Supabase・通常アプリのDBモジュールへ接続しない。結果は標準出力だけ。入力ファイルや元DBを書き換えない。請求情報を含むため出力も公開しない。実データと承認ファイルはリポジトリへ入れない。

## 金額確認の形式

承認ファイルは配列。各要素は `recordId / contractId / year / paymentIndex / seq / sourceRecordHash / amount / lineItems（省略可）/ basis`。

- `paymentIndex`は元payments配列の0始まりの位置。単回はnull、seqもnull。
- `sourceRecordHash`はbilling-jsonのcanonicalJsonをUTF-8としてSHA-256にしたもの。通常のJSON.stringifyやPostgreSQL jsonb::textを直接ハッシュした値とは同一とは限らない。
- `basis`は確認根拠。利用者回答と保存明細と原本の直接確認を区別する。
- これは金額だけの確認。現在所有者・現在請求方法を過去の確定情報として認定しない。
- 元行変更・回の不一致・未発行への過去額の指定・重複確認・不正金額は停止する。
- 担当AIが今回のバックアップへ確認回答を対応付けている。利用者回答時点のDB全体との同一性を証明するものではない。今後の元行変更はハッシュで検出する。

## 出力の読み方

- actualは請求日・入金日等の実績がある回。実在した全ての振替月が記録済みという意味ではない。
- unknownActualAmountsは保存明細／明示確認によって金額を対応付けできなかった回数。0でも実際の請求書原本と全件一致を証明しない。
- actualWithoutScheduledDateは過去の予定日が空欄の回数。請求日・入金日が空欄とは別。元IDで履歴を保全できるので、これだけを理由に過去の予定日を推測して埋めない。
- currentOwnerReferenceIdとcurrentMethodReferenceは現契約にたどった参照候補のみ。recipientConfirmedへ昇格しない。
- 旧所有者や移転日の存在／不在だけで過去の請求先を決定しない。
- readyToWriteは常にfalse。完全INSERT payload・移行許可ではない。

## 未完了の移行条件

1. 請求先の初期確認を発電所別にまとめ、例外を回ごとに指定する。全回を現所有者へ無条件確定しない。
2. 過去の請求方法と対象月を確認する。現在口座振替でも過去の単回記録を12か月に増殖させない。
3. 元記録・元seq・根拠を含む証跡の永続保存先を決める。sourceの3列だけを保存して完了としない。
4. 移行RPCで元行をロックして再照合し、新回・証跡・完了記録を原子的に保存する。ローカルでハッシュが一致しても書込時点までの一致は保証しない。
5. 新予定生成と元未発行回を対応付ける。日付が空欄の2回を捨てたり、新予定と二重計上したりしない。
6. 読取・表示・合計・訂正経路を新回へ切替え、旧画面による更新を防ぐ。移行だけ先行し二重の正本を作らない。
7. 1人利用の最小限の認証・権限、永続復旧試験、本番適用と公開の別承認。

識別テストはPGliteでDB制約を実行するが、実データ監査CLIはDBを使わない。複数接続での競合・本番の権限・復元試験ではない。
# 最新：請求書の全行payload準備

invoice-migration-payload.tsは、確認候補＋元記録＋明示した契約/発電所対応＋元行hashに固定した請求方法根拠からbilling_unitsの全保存項目と証跡を生成する。readyToWrite=falseを維持。source3列だけのアダプターから進んだが、本番INSERT用の承認・移行RPC・切替ゲートではない。

- 受領日だけある実績はreceivedのまま、請求日を捏造しない。過去の予定日null・年度と請求日年の違いは保持する。
- 単回0／分割配列位置+1、元ID・seq・全元記録・hashを保持。同年度別行をまとめない。
- 実績は非負整数の確定額・一致する明細・金額/請求先根拠必須。単回保存明細と完全一致ならsource_record、それ以外の確認額はoperator_confirmed。予定は額・明細・固定時刻null。
- hashが合っていても呼出元が日付・実績有無だけ書き換えていないかを元記録から再検査。非同期処理前に入力をコピーする。
- 現契約の請求方法から過去方法を推測しない。invoice/invoiceに対応した明示根拠が必要。振替不能・曖昧な回・不正日付は拒否。D-025は請求先の確認であり、過去方法まで自動確認済みにはしない。
- importedAtは隔離試験用の時刻。実移行RPCはDBトランザクション時刻を使い、当時の発行時刻と偽らない。初期予定はrecipient_source=confirmed／plan未接続であり、将来指定との初期同期が必要。

npm run test:billing-migrationに既存バックアップ監査・source照合・新payload試験を統合。架空4回（入金日だけの実績、分割実績、予定、同年別行）を実PostgreSQL制約へ通し、合計310円・予定null・二重挿入拒否を確認。実データをこのテストへ持ち込んでいない。元行ロック／全件照合／証跡永続保存／権限・切替・復元は次工程。
# 最新：元年度1行単位の原子的取込と移行点検（本番未適用）

20260907_invoice_import_rpc.sqlを追加。foundationの後、隔離DBのみへ適用する。import_invoice_sourceは、確認した発電所・契約の全JSON、元年度のcanonical文字列、全回payloadを受け取る。project→plan→contract→元年度→unitsをロックし、DB上の全値と再照合する。対象契約はIDで明示し、先頭契約へ推測接続しない。

- 元年度の全回を1度ずつ指定し、漏れ・重複・位置／seq不一致、日付や状態の変更、無関係な列、根拠不一致を拒否。
- 金額と明細はSQLの既存制約でも検証。保存明細根拠は単回の元明細との一致を要求。人の確認額はoperator_confirmedと根拠を保存するが、原本照合済みとは扱わない。
- 凍結日時はDBの取込トランザクション時刻を使用。クライアントの過去日時を実際の発行時刻として保存しない。
- 各回・作成イベント・操作完了・invoice_import_evidenceを同一トランザクションで保存。元年度行をUPDATE/DELETEしない。証跡は元年度全JSON・発電所/契約全スナップショット・canonical文字列/hash・各回の確認payload・採番結果・認証実行者/時刻を保持し、追記専用。

inspect_invoice_importは読み取り専用。未取込元年度、取込後に変わった元年度／発電所・契約、欠落回、作成履歴と違う回／未追跡回、未完了操作を点検する。changed_parentsは変更の影響を受ける証跡件数。単一SQLスナップショットの報告で、全ロックを保持する切替処理ではない。点検がすべて通ってもcutover_ready=falseを返し、所有者変更の旧年度ゲートは解除しない。

架空3元年度→4回を実SQLへ取込（合計310円、予定額null、同年別行保持）。最終証跡失敗・元/親変更・未掲載/重複回・金額不一致・根拠不一致・再送・証跡不変・未認証拒否をtest:billing-migrationで確認。取込後の旧記録編集・所有者変更・直接回更新も点検で検出。メモリDBでの試験であり、永続DBのバックアップ復元証明ではない。

## まだ本番移行できない理由

- この段階は元年度1行単位。全発電所／全年度の取込と切替を原子的に完了させる処理ではない。
- 新請求先指定・移転履歴・移行元のない新規回が既にある発電所は暫定拒否。先に実運用を始めて旧データを後追いで混ぜない。
- 請求のない保全専用年度、振替不能・過去方法が曖昧な回、初期将来指定との同期、将来生成との同一回照合は未対応。
- 元記録の行ロックは取込中だけ。旧アプリから後で編集されることを防ぐ書込ゲートは未接続。点検による検出を更新禁止と混同しない。
- 確認根拠は認証済み取込担当者が渡す明示入力。文字列があるだけで、D-018/D-025の承認manifestとの全件突合を代替しない。実データの方法根拠を捏造しない。
- 証跡には機微情報を含み得る。PUBLIC実行権限なし、RLS有効・ポリシー未公開を維持。実権限／トリガー、複数接続、復元・切戻し、本番承認が必要。
