# 今後の請求先一括保存（隔離検証）

`20260907_invoice_recipient_plan_rpc.sql`はfoundationとinvoice_write_rpcの後に、明示トランザクション＋draft設定の中で適用する。通常アプリへ未接続。本番用権限は公開しない。

## 実装範囲

- 確認した未発行の請求書全回について、既定の請求先と回別例外を1トランザクションで保存する。
- 例：既定B＋次回だけA。翌年の既存予定もBになる。日付や金額・状態は変えない。
- 新しい既定先の記録、各回の例外、各回の変更前後の履歴、操作完了を同時保存。旧指定は削除せずretiredにする。
- プロジェクト行、現指定、請求回をロック。現指定ID／版と全未発行回のID／版を照合。未掲載の予定追加・先行発行・更新を検出する。
- 同じ操作の再送は完了受付だけを返す。後続の新しい指定を巻き戻さない。返却後は現状態を再取得する。
- 予定日なし、review_required、今後の口座振替は拒否。発行済み・入金済みは更新しない。
- 1人利用でもauth.uidの確認とPUBLIC実行禁止は維持する。

## 検証

`npm run test:billing-db`。PGliteの架空データで次回A／翌年B、全予定の確認漏れ、先行発行、古い版、誤った例外、存在しない顧客、再送、二度目の指定、途中履歴失敗時の全取消、発行済み・入金済みの全値保持、未認証拒否を確認。

## 制限・次の接続条件

- **所有者移転RPCではない。** projects.customer_id、契約項目、所有者変更日、見込みは一切更新しない。所有者変更を保存する際は、この処理と同じトランザクション内で整合するよう統合する必要がある。
- `create_invoice_plan`で、明示された新しい請求書予定を1回作成できる。現指定ID・版を照合し、既定先を使う。年月・予定日を契約から自動展開するカレンダー生成ではない。新規生成・契約更新は同じproject行ロックを取得すること。この規約は現時点で他の全INSERT経路をDBトリガーで強制していない。複数接続による競合検証は残る。
- 単回plan編集RPCもproject→現指定→回の順でロックし、現指定の例外表とrevisionを原子的に同期する。既定先と同じなら例外を除去、異なるなら例外追加。空欄は現指定から切り離してunconfirmedを保持。旧指定の例外は変更しない。履歴失敗時の全取消を検証済み。
- 発行・訂正時は回の確定請求先が正本。例外表を発行済み／入金済みへ再適用してはいけない。過去の指定を残すため、発行した回の例外を削除・再生成する処理は追加していない。UIの「今後の例外」表示はplanned回だけを対象にする必要がある。
- 旧指定は参照用に残る。指定表の直接UPDATEを防ぐ実運用RLS／権限の設計・試験は未完了。PUBLIC禁止や行ロックだけを全体の安全証明としない。
- 元所有者の購入情報の分類、移転スナップショット、口座振替の過去月保護、旧顧客の請求履歴画面、移行・復旧・本番反映は別途残る。

## 明示的新規作成の制限

- 現指定より前の日付、複数契約、請求書以外の現契約、空欄・古い指定は拒否する。凍結額はnullのまま、予定と作成履歴を原子的に保存する。
- 同じ操作の再送や同じ発電所・occurrence_keyの重複は保護する。ただし同じ業務上の回に違うキーを付ければ防げない。元の回識別／移行計画と統一したキー生成が必要で、通常アプリにはまだ公開しない。
- 移行済み／未移行の元年度記録との突合は未接続。これを自動カレンダー生成・安全な本番新規作成の完成と扱わない。
- 1回だけを未確認に戻しても、既定先は維持する。その回は既定先で再上書きしない。将来の生成器は既存回を再作成・上書きせず、新しい回だけ作ること。
